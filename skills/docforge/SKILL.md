# DocForge：高质量技术文档

将有限且可访问的源材料，转化成一份让目标读者能理解、核查和采取行动的技术文档。技能自带工作流，
不依赖目标仓库中的 `AGENTS.md`、脚本、模板或特定目录。

## 适用边界

- 适用：解释系统或模块如何工作、描述架构/接口/数据流、复盘变更或故障、整理设计方案、撰写工程集成指南。
- 不适用：改一句话、没有可用材料却要求虚构细节、只要求生成一张不承载技术论点的图片。
- 先确定读者、目标问题、输出语言和可用材料。目标含糊且会导致不同文档时，先提出一个简短澄清问题；
  否则基于材料作出最小且明确的范围假设。

## 运行黑板

在用户指定的位置创建独立运行目录；未指定时，使用当前项目的 `.docforge/runs/<主题短名>/`。只把本次
生成的中间物写入该目录，至少维护：

```text
boundary.md       # 读者问题、纳入/排除范围、材料清单
facts.json        # 可核查的事实与关系
outline.md        # 章节目的、读者推进、支撑事实
diagrams/         # 最终图片、图稿、trace sidecar
draft.md          # 待审正文
review.md         # 审稿结论与可执行修复项
document.md       # 仅在通过审稿后生成的成品
```

这些是工作产物而非对用户的额外要求。若用户只需要正文，可在交付后保留 `document.md` 与必要图片，
但仍在生成过程中完成同等强度的取据和核验。

## 第一关：界定与取据

先写 `boundary.md`：用一句话说明文档必须回答的问题，列出读者、in scope、out of scope 和实际阅读的
材料。范围外的有趣信息不进入事实账本。

再写 `facts.json`。每条事实使用稳定 id，并至少包含：

```json
{
  "id": "comp:auth-gateway",
  "kind": "component",
  "claim": "鉴权入口位于 auth-gateway。",
  "provenance": [{"type": "file", "ref": "src/auth/gateway.ts:42", "quote": "..."}],
  "confidence": "certain"
}
```

- 使用节点表达组件、接口、数据、事件、步骤和概念；用关系表达调用、依赖、包含、先后或因果。关系也必须
  有自己的 id 和 provenance。
- 来源引用必须精确到文件/行、文档章节、commit、issue、URL 或日志位置。引文只保留足以支撑论点的片段。
- 从多个事实得出的判断标为 `inference`，置信度最多为 `likely`，并列出支撑的 fact id。无法证实的内容
  记为 open question，而不是写成事实。
- 不要在此阶段写叙事或画图；事实少而准确优于堆砌。

## 第二关：组织、配图与成文

先写 `outline.md`。每节必须写明：本节结论、它回答的读者问题、支撑 fact id，以及它如何自然引向下一节。
通常按“全貌 → 关键机制 → 约束/边界 → 实际影响或下一步”推进；让材料而非固定模板决定最终结构。

正文写入 `draft.md`：

- 每节首段先给结论，再给证据和细节；一节只承担一个主观点。
- 在非显而易见的技术论断旁紧凑标注来源，例如 `（src/auth/gateway.ts:42）`。
- 用真实名称、接口、路径和条件替代泛泛描述；明确写出范围外内容和 open questions。
- 正文使用用户指定语言；源码、命令、路径、ID、标识符和原文引述保持原样。

## 配图政策（硬规则）

只为承载关键关系的论点配图，一图只表达一个问题。所有面向读者的图都必须使用 ChatGPT 图像生成能力，
并选择**当前环境可用的最新、最强图像生成模型**：调用前查询官方 OpenAI 文档或当前工具的模型列表；
工具允许指定模型时显式选旗舰图像模型，不能指定时使用该工具的默认图像模型。

不得用 Mermaid、手写 HTML/SVG、Canvas、Graphviz、代码绘图再导出位图、截图拼贴，或其他图像模型替代。
如果没有可用的 ChatGPT 图像生成能力，说明阻塞；不得假装用代码图满足了图表要求。

对每张图执行：

1. 先在 `diagrams/<id>.brief.md` 写图稿：单一意图、读者应看懂的关系、节点/箭头/分组/标签、对应 fact id，
   以及禁止出现的无据内容。
2. 提示词要求清晰、克制的技术插图，足够留白、标签可读且匹配正文语言；严格按图稿表达，禁止添加组件、
   数据流、因果或结论。
3. 生成最终 PNG（或工具原生的无损位图）到 `diagrams/`，人工复核文字、箭头、分组、关系与图稿一致。
   有错误就编辑或重生成，不能把图像模型臆造当成事实。
4. 写 `diagrams/<id>.trace.json`，把图中每个可见节点、箭头、分组和标签映射到真实 fact id。若需机器核验，
   可增加只嵌入图片和事实图例的 HTML 包装页；包装页不得绘制或修改图中的关系。

## 第三关：独立审稿

写 `review.md`，逐项核查：

1. **可溯源性**：每个事实性句子和图中可见元素是否能回到 `facts.json` 的 provenance；缺事实时回到取据，
   有事实但未引用时回到写作。
2. **结构与清晰度**：标题是否回答读者问题、章节是否递进、每节结论是否先行、图是否有文字导读。
3. **技术准确性**：范围、条件、例外和推断是否诚实；是否混淆观察到的事实与推断。
4. **图像质量**：是否由当前旗舰可用 ChatGPT 图像模型生成；是否一图一义、可读、无模型虚构，且 trace 完整。
5. **可交付性**：读者语言正确，术语一致，关键 open questions 明示。

将每个问题写成可执行 finding，标明归属“取据”或“写作/配图”。修复后从最早受影响的关卡重新核验；
最多循环三次。只有不存在 blocker 且所有关键论点和图都可溯源时，才将 `draft.md` 复制为 `document.md`。

## 不可妥协的原则

- 无据不写，无据不画；宁可明确未知，也不自信编造。
- 推断永远显式标示，且不高于 `likely`。
- 文档服务读者的决策与理解，不是事实清单或模型生成图片的展览。
